# Requirements Document

## Introduction

This document specifies the requirements for a Real-Time A2A Chat Client — a full-stack, containerized chat application that acts as a client for an Agent2Agent (A2A) compliant server. The system supports synchronous A2A message exchange via JSON-RPC 2.0, handles the A2A `input-required` task state for multi-turn conversations, and displays real-time asynchronous progress updates pushed via webhooks from an external MCP server. Chat history is persisted in DynamoDB to enable conversation resumption across sessions. The technology stack consists of a React (Vite) frontend with socket.io-client, a Node.js/Express/socket.io/axios/AWS SDK backend, and Docker/docker-compose orchestration targeting AWS EC2 deployment.

## Glossary

- **Backend**: The Node.js Express server that proxies A2A requests, manages WebSocket connections, and receives webhook callbacks.
- **Frontend**: The React single-page application that provides the chat user interface and maintains a real-time WebSocket connection to the Backend.
- **A2A_Server**: An external Agent2Agent protocol-compliant server that the Backend communicates with via JSON-RPC 2.0.
- **MCP_Server**: An external server that sends asynchronous progress updates to the Backend webhook endpoint during agent task execution.
- **Agent_Card**: A JSON document served by the A2A_Server at its well-known endpoint, containing agent metadata such as name, description, and skills.
- **Context_ID**: A UUIDv4 identifier generated by the Frontend to uniquely identify a conversation session.
- **Task_ID**: An identifier returned by the A2A_Server to track a specific task, used to resume paused tasks.
- **Task_State**: The state of an A2A task, either `completed` or `input-required`.
- **Socket_Room**: A Socket.io room identified by a Context_ID, used to route real-time updates to the correct client session.
- **Webhook**: An HTTP POST callback sent by the MCP_Server to the Backend to deliver asynchronous progress updates.
- **JSON_RPC_Payload**: A JSON-RPC 2.0 formatted request object containing method, params, id, and jsonrpc fields.
- **Status_Indicator**: A dedicated UI element in the Frontend that displays live progress updates from the MCP_Server.
- **Docker_Compose**: The orchestration tool that wires the Backend and Frontend containers together for deployment.
- **Chat_Session**: A persisted record in DynamoDB representing a conversation, identified by a Context_ID, containing the agent URL, agent metadata, messages, and task state.
- **DynamoDB_Table**: An AWS DynamoDB table used to persist Chat_Session data for conversation history and resumption.
- **Session_List**: A list of previously saved Chat_Sessions displayed in the Frontend sidebar, allowing the user to resume a past conversation.

## Requirements

### Requirement 1: Backend Server Initialization

**User Story:** As a developer, I want the Backend to initialize with proper middleware, so that the Frontend can communicate securely with the Backend across origins.

#### Acceptance Criteria

1. THE Backend SHALL initialize an Express server with CORS enabled for the Frontend origin.
2. THE Backend SHALL parse all incoming request bodies as JSON.
3. THE Backend SHALL listen on port 3001 for incoming HTTP requests.

### Requirement 2: Socket.io Hub Setup

**User Story:** As a developer, I want the Backend to manage WebSocket connections via Socket.io, so that real-time progress updates can be routed to the correct client session.

#### Acceptance Criteria

1. THE Backend SHALL initialize a Socket.io server attached to the Express HTTP server.
2. WHEN a client emits a `join_room` event containing a Context_ID, THE Backend SHALL add the connecting socket to the Socket_Room identified by that Context_ID.
3. WHEN a client disconnects, THE Backend SHALL remove the socket from its associated Socket_Room.

### Requirement 3: Agent Discovery Endpoint

**User Story:** As a user, I want to discover an A2A agent's capabilities by providing its base URL, so that I can see the agent's name, description, and skills before chatting.

#### Acceptance Criteria

1. WHEN the Backend receives a POST request to `/api/discover` with a JSON body containing an `agentUrl` field, THE Backend SHALL make an HTTP GET request to `${agentUrl}/.well-known/agent.json`.
2. WHEN the A2A_Server returns a valid Agent_Card, THE Backend SHALL respond with the parsed Agent_Card JSON and an HTTP 200 status code.
3. IF the HTTP GET request to the A2A_Server fails or returns a non-200 status, THEN THE Backend SHALL respond with an appropriate HTTP error status code and an error message describing the failure.

### Requirement 4: Message Sending Endpoint

**User Story:** As a user, I want to send messages to an A2A agent and receive responses, so that I can have a conversation with the agent.

#### Acceptance Criteria

1. WHEN the Backend receives a POST request to `/api/message` with a JSON body containing `agentUrl`, `contextId`, and `userText` fields, THE Backend SHALL construct a JSON_RPC_Payload with method `sendMessage`, a newly generated UUID as the `id`, and the `contextId` and `userText` in the params.
2. WHEN the request body includes an optional `taskId` field, THE Backend SHALL include the `taskId` in the JSON_RPC_Payload params to resume a paused task.
3. THE Backend SHALL send the constructed JSON_RPC_Payload as an HTTP POST to the provided `agentUrl`.
4. WHEN the A2A_Server responds successfully, THE Backend SHALL extract the agent text part, the Task_State, and the Task_ID from the response and return a JSON object containing `text`, `state`, and `taskId` fields with an HTTP 200 status code.
5. IF the HTTP POST to the A2A_Server fails or returns an error, THEN THE Backend SHALL respond with an appropriate HTTP error status code and an error message describing the failure.

### Requirement 5: Webhook Listener Endpoint

**User Story:** As a user, I want to see real-time progress updates from the agent while it processes my request, so that I know what the agent is doing.

#### Acceptance Criteria

1. WHEN the Backend receives a POST request to `/webhook` with a JSON body containing `contextId` and `status` fields, THE Backend SHALL emit a `progress_update` event with the `status` value to the Socket_Room matching the provided `contextId`.
2. THE Backend SHALL respond to the webhook sender with an HTTP 200 status code immediately after emitting the event.
3. IF the webhook payload is missing the `contextId` field, THEN THE Backend SHALL respond with an HTTP 400 status code and an error message.

### Requirement 6: Frontend Sidebar and Agent Connection

**User Story:** As a user, I want a sidebar where I can enter an agent URL and connect, so that I can discover and interact with A2A agents.

#### Acceptance Criteria

1. THE Frontend SHALL display a sidebar containing a text input field for "Agent Base URL" and a "Connect" button.
2. WHEN the user clicks the "Connect" button, THE Frontend SHALL send a POST request to the Backend `/api/discover` endpoint with the entered agent URL.
3. WHEN the Backend returns a valid Agent_Card, THE Frontend SHALL display the agent name, description, and skills in an information panel within the sidebar.
4. WHEN the Backend returns a valid Agent_Card, THE Frontend SHALL generate a new Context_ID as a UUIDv4 value.
5. WHEN a Context_ID is generated, THE Frontend SHALL establish a Socket.io connection to the Backend and emit a `join_room` event with the Context_ID.
6. IF the discovery request fails, THEN THE Frontend SHALL display an error message to the user in the sidebar.

### Requirement 7: Chat Area and Message Display

**User Story:** As a user, I want a main chat area to view my conversation history with the agent, so that I can follow the conversation flow.

#### Acceptance Criteria

1. THE Frontend SHALL display a main chat area with a scrollable message history.
2. THE Frontend SHALL visually distinguish user messages from agent messages using different styling.
3. THE Frontend SHALL display a chat input box and a "Send" button pinned to the bottom of the chat area.
4. THE Frontend SHALL display a Status_Indicator element directly above the chat input box for showing live progress updates.
5. WHEN a new message is added to the conversation, THE Frontend SHALL automatically scroll the chat area to the most recent message.

### Requirement 8: Sending and Receiving Chat Messages

**User Story:** As a user, I want to send messages and receive agent responses in the chat, so that I can have a productive conversation with the A2A agent.

#### Acceptance Criteria

1. WHEN the user submits a message via the chat input, THE Frontend SHALL append the user message to the messages array and display the message in the chat area.
2. WHEN the user submits a message, THE Frontend SHALL send a POST request to the Backend `/api/message` endpoint with the `agentUrl`, `contextId`, `userText`, and the current `activeTaskId` if one exists.
3. WHEN the Backend returns a successful response, THE Frontend SHALL append the agent response text to the messages array and display the message in the chat area.
4. WHEN the Backend returns a successful response, THE Frontend SHALL set the `agentStatus` to null to clear the Status_Indicator.
5. WHEN the Backend returns a response with Task_State `input-required`, THE Frontend SHALL set `isInputRequired` to true and store the returned Task_ID as the `activeTaskId`.
6. WHEN the Backend returns a response with Task_State `completed`, THE Frontend SHALL set `activeTaskId` to null.
7. WHEN the user submits a message, THE Frontend SHALL set `isInputRequired` to false.

### Requirement 9: Real-Time Progress Updates

**User Story:** As a user, I want to see live status updates while the agent processes my request, so that I have visibility into the agent's progress.

#### Acceptance Criteria

1. WHEN the Frontend receives a `progress_update` event via Socket.io, THE Frontend SHALL update the `agentStatus` state with the received status value.
2. WHILE `agentStatus` contains a non-null value, THE Frontend SHALL display the status text in the Status_Indicator element (e.g., "⏳ Agent is: calling salesforce").
3. WHILE `agentStatus` is null, THE Frontend SHALL hide or clear the Status_Indicator element.

### Requirement 10: Input-Required State Handling

**User Story:** As a user, I want a visual indication when the agent needs more input from me, so that I know to provide additional information.

#### Acceptance Criteria

1. WHILE `isInputRequired` is true, THE Frontend SHALL visually highlight the chat input box to indicate the agent is awaiting clarification.
2. WHILE `isInputRequired` is true, THE Frontend SHALL change the placeholder text of the chat input box to indicate the agent needs additional input.

### Requirement 11: Frontend State Management

**User Story:** As a developer, I want well-defined state variables in the Frontend, so that the application behavior is predictable and consistent.

#### Acceptance Criteria

1. THE Frontend SHALL maintain an `agentUrl` state variable storing the confirmed URL of the connected A2A_Server.
2. THE Frontend SHALL maintain a `contextId` state variable storing the UUIDv4 generated upon successful agent connection.
3. THE Frontend SHALL maintain a `messages` state variable as an array of objects, each containing `role` and `text` fields.
4. THE Frontend SHALL maintain an `agentStatus` state variable as a string, defaulting to null.
5. THE Frontend SHALL maintain an `activeTaskId` state variable as a string, defaulting to null.
6. THE Frontend SHALL maintain an `isInputRequired` state variable as a boolean, defaulting to false.

### Requirement 12: Backend Docker Container

**User Story:** As a developer, I want the Backend packaged as a Docker container, so that it can be deployed consistently on AWS EC2.

#### Acceptance Criteria

1. THE Backend Dockerfile SHALL use `node:18-alpine` as the base image.
2. THE Backend Dockerfile SHALL expose port 3001.
3. THE Backend Dockerfile SHALL set the start command to launch the Node.js server.
4. THE Backend Docker container SHALL install only production dependencies.

### Requirement 13: Frontend Docker Container

**User Story:** As a developer, I want the Frontend packaged as a Docker container with a multi-stage build, so that only optimized static assets are served in production.

#### Acceptance Criteria

1. THE Frontend Dockerfile SHALL use a multi-stage build: a Node build stage to compile the React application and an `nginx:alpine` stage to serve the static assets.
2. THE Frontend Dockerfile SHALL expose port 80.
3. THE Frontend Dockerfile SHALL configure environment variables (e.g., `VITE_API_URL`) to route Frontend API and Socket.io calls to the Backend container.

### Requirement 14: Docker Compose Orchestration

**User Story:** As a developer, I want a docker-compose configuration that wires both services together, so that the entire application can be started with a single command.

#### Acceptance Criteria

1. THE Docker_Compose file SHALL define two services: `api` for the Backend and `web` for the Frontend.
2. THE Docker_Compose file SHALL map the Backend port 3001 to the host so that the external A2A_Server can reach the webhook endpoint at `http://<host-ip>:3001/webhook`.
3. THE Docker_Compose file SHALL map the Frontend port 80 to the host for user access.
4. THE Docker_Compose file SHALL configure networking so that the Frontend container can communicate with the Backend container.

### Requirement 15: Chat History Persistence in DynamoDB

**User Story:** As a user, I want my chat history saved automatically, so that I do not lose my conversation if I close the browser or refresh the page.

#### Acceptance Criteria

1. WHEN the Backend successfully processes a `/api/message` request and receives a response from the A2A_Server, THE Backend SHALL persist the user message and the agent response to the DynamoDB_Table, keyed by the `contextId`.
2. THE Backend SHALL store the following fields in each Chat_Session record: `contextId`, `agentUrl`, `agentName`, `messages` array, `activeTaskId`, `isInputRequired`, `createdAt` timestamp, and `updatedAt` timestamp.
3. WHEN a new conversation is started (first message for a given `contextId`), THE Backend SHALL create a new Chat_Session record in the DynamoDB_Table.
4. WHEN a conversation already exists for the given `contextId`, THE Backend SHALL append the new messages to the existing Chat_Session record and update the `updatedAt` timestamp.
5. IF the DynamoDB write operation fails, THEN THE Backend SHALL log the error and still return the A2A_Server response to the Frontend without blocking the chat flow.

### Requirement 16: Chat History Retrieval

**User Story:** As a user, I want to retrieve my past conversations, so that I can review previous interactions and resume where I left off.

#### Acceptance Criteria

1. WHEN the Backend receives a GET request to `/api/sessions`, THE Backend SHALL query the DynamoDB_Table and return a list of Chat_Session summaries sorted by `updatedAt` in descending order.
2. THE Backend SHALL include `contextId`, `agentName`, `updatedAt`, and a preview of the last message in each Chat_Session summary.
3. WHEN the Backend receives a GET request to `/api/sessions/:contextId`, THE Backend SHALL retrieve the full Chat_Session record from the DynamoDB_Table and return it with an HTTP 200 status code.
4. IF the requested `contextId` does not exist in the DynamoDB_Table, THEN THE Backend SHALL respond with an HTTP 404 status code and an error message.

### Requirement 17: Chat Resumption

**User Story:** As a user, I want to resume a previous conversation with an agent, so that I can continue where I left off without losing context.

#### Acceptance Criteria

1. THE Frontend SHALL display a Session_List in the sidebar showing previously saved conversations.
2. WHEN the user selects a session from the Session_List, THE Frontend SHALL send a GET request to `/api/sessions/:contextId` to retrieve the full Chat_Session.
3. WHEN the full Chat_Session is retrieved, THE Frontend SHALL restore the `agentUrl`, `contextId`, `messages`, `activeTaskId`, and `isInputRequired` state from the Chat_Session data.
4. WHEN the full Chat_Session is retrieved, THE Frontend SHALL establish a Socket.io connection to the Backend and emit a `join_room` event with the restored Context_ID.
5. WHEN the full Chat_Session is retrieved, THE Frontend SHALL display the agent name, description, and skills in the sidebar information panel.
6. WHILE a resumed Chat_Session has `isInputRequired` set to true, THE Frontend SHALL visually highlight the chat input box and update the placeholder text to indicate the agent is awaiting clarification.
